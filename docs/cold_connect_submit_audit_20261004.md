# Cold connection submission and audit record integrity

The first release completed a maker02 observation from 2026-10-04 17:47:16.117 to 18:47:16.117 UTC. It reduced causal WS-ready→submit place P99/P999 from 338.655/400.221us to 275.834/332.259us (6,170 baseline vs 4,111 new observed rows); prep→signed median fell from 53.965 to 32.234us. These different live windows are not a controlled A/B experiment. Three malformed rows in the shared hourly audit file censor the first release's completeness claims; the original raw prefixes and hashes are preserved in the hexbot evidence directory.

Two remaining failure mechanisms required a follow-up:

* A reused callback DELETE (zhu02, root attempt 8796) queued on the order reactor for 658.332us at 18:27:12.451495 UTC, near multiple simultaneous slow connection retirements and creation of new blocking workers. A causal place also queued for 429.293us. TLS polling had moved off the reactor, but Tokio 1.52.3 blocking/pool.rs spawn_task still synchronously calls spawn_thread on the caller when its blocking pool has no idle worker. The old benchmark prewarmed that pool. The live timestamps support association, not per-event CPU attribution or proof of the entire historical 1.822485ms callback.
* Account-specific audit workers each used an independent BufWriter to append to the same order-audit-{hour}.jsonl. Serialization can flush mid-record; append mode does not serialize multiple writes. One account's lifecycle row, another HTTP phase and a cancel attempt were interleaved. This is a persistence error, separate from economic order-state ownership.

## Ownership, queues and boundaries

ord-connect-tx is an explicitly prestarted SCHED_OTHER background owner (CPU4 on maker02), initialized after core-plan validation and before runtime handles are published. Its bounded FIFO capacity is 64. Producers transfer owned cold-connection submission closures through nonblocking try_send; the owner only invokes the captured original Handle.spawn_blocking and never waits for HTTP. Tokio pool locks and synchronous worker creation occur on this owner. Maintenance/RPC pools are separate because their workers can synchronously wait for the same HTTP connections. No new mutable strategy/account authority or business execution queue is introduced. Reused requests do not use the lane.

The capacity-one connection reply retains cancellation and the original reactor registration. A queued caller that has disappeared is discarded before starting a worker; a running owned future observes the closed receiver. Full/disconnected submission fails before HTTP, with no POST replay. The absolute connect deadline covers submit queue pickup, OS worker creation, worker pickup and TLS; an outer deadline also cancels work while it is queued. connect_worker_queue_ns measures this entire handoff up to the first worker poll, rather than hiding it in TLS. Background-only telemetry reports depth, sampled high-water, admitted/dequeued, rejection and submission panic counts. Strict background affinity validation applies before startup readiness. The process startup lock is startup-only and serializes concurrent init callers.

Each existing account audit owner retains its lifecycle map, record buffer and bounded incoming queue. Serialization goes into a local reusable 64KiB record batch, including newline, before any file write. Complete batches append under a Unix file advisory lock, including periodic flush, large records, hour rotation and drop. This cold file lock preserves the shared artifact names/readers and coordinates cooperating processes without adding a global mutable writer map or a second lifecycle queue. All appenders in the deployed process use this protocol. No strategy, private owner, Fast/Cancel owner or I/O runtime takes this lock, formats audit JSON or writes files. The existing one-second flush and shutdown drain remain. A failed append poisons the writer rather than replaying a possibly partly appended batch or growing its buffer; failure is reported and requires explicit recovery. This is not a transactional durability/fsync guarantee. A future consolidation of background exporters can use one artifact owner; introducing another admission/overflow boundary is unnecessary for this integrity fix.

## Cold recovery read correctness

ARM also exposed a pre-existing test reading the reporting projection immediately after an asynchronous lifecycle update. That projection may lag; it is not a FIFO barrier. The test now flushes the existing execution/lifecycle lane and queries recovery_order on its sole owner, including explicit Filled status/reservation assertions. Cold reconcile identity lookup retains its immutable runtime-index primary path and uses that same existing bounded ordered owner query for a missing-index fallback. Owner queue failure fails closed as lifecycle_owner_unavailable. Hot cancel preparation never calls this fallback. No new shared account admission gate, queue or owner is introduced. A focused real-owner test removes the runtime identity, validates fallback side/instance/slot, and rejects wrong OID/COID. This incrementally removes reporting state as a cold recovery authority without expanding shared-state use on critical lanes.

## Validation

Focused tests exercise full FIFO rejection and subsequent recovery, ordering, submit owner isolation, queued/running cancellation, submission and connection worker failures, concurrent runtime startup, stalled TLS deadline and zero HTTP bytes before connection success. A pre-existing latency CSV test waited only 100 yields for its background writer and failed under ARM housekeeping scheduling. It now asserts the bounded flush message directly, avoiding a timing-dependent file existence check; production recorder behavior is unchanged. Four concurrent account writers append 600 rows, including records over 64KiB, varied flush boundaries and drop; every row is parsed, unique, owner-correct and in per-account order. Hour rotation and write-error/no-replay behavior are checked. Existing exchange tests retain private-event idempotence, replay, overflow, reservation fencing and owner routing.

Maker02 release benchmark forces a fresh empty blocking pool on every round, with six simultaneous cold tasks and no network or trading. The measured boundary is hot-task enqueue→first poll; runtime construction, waits and sorting are outside it. N=1,000 per mode; CPU0/nice19 caller and CPU1/nice19 background. Final run: direct submission median/P99/P999/max = 39.202/50.573/89.832/105.305us; background submission = 3.756/4.892/5.858/8.591us. Submit queue sampled high-water=6, final depth=0, admitted/dequeued=6,000/6,000, rejected=0, submission panics=0. Both modes create 6,000 workers. This demonstrates removal of synchronous thread-creation interference, not the numerical live distribution. Final benchmark output and queue statistics are stored alongside this document.

The final SDK/bot pair must complete a new 60-minute live window with unchanged configurations, exact account/domain/root joins, valid raw JSONL prefixes, zero audit/submit queue loss and retained private-event correctness before acceptance. First-release data with malformed rows must remain explicitly censored.
