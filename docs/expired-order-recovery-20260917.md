# Recover expired runtime orders from complete no-fill evidence

On maker02, two placement transport failures at 2026-09-17 00:15:01/02 UTC remained NewOrderTimeout until 00:33:16. At 00:20:01 both asset cancellation endpoints had already replied successfully with no uncanceled orders, but single-order GETs returned JSON null. The runtime path waited for three complete passes of token-retirement evidence; the existing complete historical no-fill audit was restricted to restart recovery.

The legacy dual-slot fast path did not activate: live connection owners permanently retain the account Reconcile permits, while the old lookup code tries to borrow a second permit from that same pool. This change removes the expired-order recovery dependency on that fast path. It does not share owner clients or weaken null/timeout handling for active orders. A future migration can route all dual reads as independent messages and combine their replies outside connection owners.

After an expiry-scoped market cancel succeeds for every requested asset, absent orders can now enter the existing authenticated historical trade audit. All pages must complete with exact maker/taker order identities, with no matching trade and no observed matched quantity or associated trade obligation. Transport errors, malformed/incomplete pagination, unrelated order audit errors, identity mismatch and any matching trade leave reservations intact. Query parameters retain the ended market filter on every page; the filter avoids scanning unrelated account history when a process-seeded coid counter predates the placement time. The 64-page cap and HTTP deadlines remain in force; exhaustion cannot authorize release.

The lifecycle owner atomically revalidates the candidate identity and no-fill preconditions before committing cancellation and its authoritative zero-match audit. It rejects a newer match or stronger terminal status without mutation. Cleanup uses the owner's explicit completion result, so a lagging cold mirror cannot reintroduce a retry or overwrite a private fill. Duplicate completion preserves audit and reservation state.

**Architecture.** Recovery and its HTTP reads remain on the existing cold expiry/recovery paths. `ApplyZeroFillRecovery` is an owned message on the existing bounded priority lifecycle lane; its writer performs the final check and update in one turn. No new mutable global state, lock, queue or worker is added. Quote processing, instance routing, disk format and CPU topology are unchanged. Existing cold synchronous compatibility calls remain outside quote callbacks. Historical audit can add background I/O to an expiry attempt; it runs only for eligible absent orders and remains fail-closed on incomplete evidence.

**Validation.** Account/engine/exchange suites passed 315/114/839 tests (1,268 total); the final focused recovery suite passed 5 tests after removing a redundant cold-mirror read. Tests cover the two runtime-null incident shapes on both sides, a complete multi-page no-fill audit, matching maker trades on later pages, market-filter/cursor preservation, ineligible active/failed-cancel scopes, partial sibling recovery, wrong-instance rejection, incomplete history, duplicate completion and a private match arriving during historical I/O. An account-owner test separately proves that a stale no-fill candidate cannot erase already-queued matched evidence.

The focused local debug microbenchmark measures owner dispatch, precondition validation, account commit and reply, with 300 events per mode and 600 preallocated orders. It excludes network, disk and strategy work. Both modes had observed queue high water 1 and overflow 0. Median/P99/P999/max were 26.500/118.172/3277.589/3277.589 us for the prior unconditional commit and 26.529/139.722/161.034/161.034 us for conditional commit. These small-sample timings are validation of the boundary, not a production latency improvement claim. The benchmark does not estimate remote recovery time.

A read-only authenticated verification from maker02 at 04:06:37 UTC returned HTTP 200/null for both historical order IDs and a complete empty market-filtered trade page in 130 ms. This confirms the query route works without claiming what it returned during the original incident.

The recorded incident proves the missing recovery branch; it does not show what the historical endpoint would have returned at 00:20. A simulated complete no-fill response resolves on the first eligible pass. Live time-to-recovery must be measured when a comparable incident occurs; no fixed timeout or invented zero-fill status is introduced.

API semantics: [authenticated trades and pagination](https://docs.polymarket.com/api-reference/trade/get-trades), [cancellation result fields](https://docs.polymarket.com/api-reference/trade/cancel-all-orders). Order absence alone is not used as fill evidence.
