# Cancel late maintenance reservations before submission

On maker02 at 2026-10-02 19:54:21 UTC, a split worker timed out waiting for a cold account-owner reservation result. The already accepted owner command subsequently reserved 160 USDC. The caller returned an admission failure before entering `run_split_one`, so it never persisted a wallet intent or posted the split. Recovery correctly refused to infer success from missing evidence, but the abandoned reservation blocked later inventory seeding.

The reservation RPC now distinguishes failure to enqueue from timeout after an accepted enqueue. Only the latter retains an `AbortMaintenanceAdmission` message behind the original reservation on the same bounded 4096-command FIFO lane. The cold wallet worker waits for queue capacity if necessary; no quote/private callback uses this path. The sole account owner releases only a still-Reserved operation with neither a transaction ID nor a wallet submission intent. Submitted, uncertain, confirmed and signed-intent operations remain fail-closed. Repeated cleanup is idempotent. Disconnection is reported as cleanup unavailable and keeps admission closed.

There is no new mutable runtime field, account authority, worker, queue or hot-path work. The existing cold compatibility RPC remains an incremental migration target for a typed asynchronous maintenance state machine. The cleanup's bounded backpressure is deliberate: a timed-out admission must not drop its compensating message and leave a late reservation behind. Queue capacity and FIFO ordering remain unchanged, and private lifecycle uses its separate higher-priority lane.

Regression coverage holds the account owner until the caller times out, then verifies reserve-before-abort ordering, duplicate cleanup, preserved instance balances and persistence/restart. A full-lane test verifies the cleanup is retained until capacity returns. Submission/uncertainty/intent evidence tests verify that cancellation cannot release a possibly submitted operation. This is correctness work on a cold path; hot-path latency and CPU are validated in the subsequent live hour.

The incident operation predates this cleanup. Any one-off recovery must stop the live process, preserve checkpoint/WAL backups, verify the exact operation identity and timestamp against the failed call path, require no submission evidence, and use the account ledger API. Missing transaction evidence alone is not general permission to release older uncertain operations.
